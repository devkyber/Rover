# 코드 해설 — 이론이 어느 줄에 있는가

> 원리는 [01](01_이론_오도메트리와_ESKF.md), 값 맞추기는 [03](03_튜닝과_NIS.md),
> 실행은 [04](04_실행_가이드.md).
>
> 이 문서는 **지도**다. 식 하나를 코드 한 줄에 연결하는 것이 목적이다.

## 설계 원칙 세 가지

1. **상수는 [`config.py`](../rover/config.py) 한 곳에만.**
   다른 파일에서 숫자를 새로 만들지 않는다. 포트·치수·`Q`·`R`·임계값 전부.
2. **읽기와 쓰기를 분리.**
   `dxl_reader.py`는 안전하고, `dxl_control.py`는 로버를 움직인다.
   섞으면 "조회하려다 굴러가는" 사고가 난다.
3. **부호는 한 곳에서만.**
   `config.WHEEL_SIGN`을 조종(`dxl_control.drive`)과 오도메트리
   (`odometry.wheel_speeds_mps`)가 **같이** 읽는다. 그래서 조종 방향과
   추정 방향이 구조적으로 어긋날 수 없다.

## `eskf.py` — 식과 줄의 대응

### 쿼터니언 도우미

| 함수 | 이론 |
|---|---|
| `quat_multiply(p,q)` | `p ⊗ q` |
| `quat_to_rot(q)` | `R(q)`, **월드←바디** |
| `small_angle_to_quat(δθ)` | `exp(δθ)` |
| `skew(v)` | `[v]ₓ` ([01 §1](01_이론_오도메트리와_ESKF.md)) |

### `create_state()`

명목상태 `p, v, q, bg, ba` + `P` (15×15) + `nis` 수집함.

`P`의 초기 대각을 보면 **무엇을 얼마나 모른다고 시작하는지** 알 수 있다.
The initial gyro-bias variance is `1e-6 (rad/s)^2`. `create_state()` starts
with zero bias, but normal `Odometry` startup replaces that estimate with the
stationary gyro mean before prediction. Later ZARU updates can refine it.
The initial variance is a modeling choice, not a measured calibration result.

### `predict()` — [01 §7](01_이론_오도메트리와_ESKF.md)

| 계산 | 식 |
|---|---|
| 입력 보정 | `ω = gyro_raw − bg`, `a = accel_raw − ba` |
| 병진 적분 | `a_world = Ra + g_world`, `p`·`v` 적분 |
| 회전 적분 | `q ← q ⊗ exp(ω dt)` |
| `F` 구성 | [01 §7.3](01_이론_오도메트리와_ESKF.md)의 표와 1:1 |
| `Q` 구성 | **`σ²·dt`** — `(σ·dt)²`가 아니다 |

> `predict()`의 `Q` 구성 주석이 그 버그를 설명한다. `dt=0.01`에서 `Q`가 100배
> 작아서, 필터가 자기 자세를 과신해 중력 업데이트가 기울기를 못 고쳤다.

### `_ekf_update()` — [01 §5.2](01_이론_오도메트리와_ESKF.md)

다섯 관측이 **전부 이 함수 하나**를 쓴다. 각 관측이 하는 일은 `z, h, H, R`
네 개를 만드는 것뿐이다.

| 계산 | 식 |
|---|---|
| innovation | `y = z − h` |
| innovation covariance | `S = HPHᵀ + R` |
| Kalman gain | `K = PHᵀS⁻¹` |
| covariance update | **Joseph form** `P = (I−KH)P(I−KH)ᵀ + KRKᵀ` |
| state correction | `δx = Ky`, 이후 `_inject(state, δx)` |
| consistency | `NIS = yᵀS⁻¹y` ([03](03_튜닝과_NIS.md)) |

### `_inject()`

`⊞` 연산자. 전부 덧셈이고 자세만 `q ⊗ exp(δθ)`.

> **여기가 국소(local) 오차 관례를 정하는 곳이다.**
> 모든 `F`와 `H`가 이 선택을 따라야 한다. `test_filter.py`가
> **같은 `⊞`로** 수치미분을 하므로 관례 불일치까지 잡힌다.

> **알려진 단순화:** 표준 ESKF는 주입 후 `P`에 리셋 야코비안
> `G = I − ½[δθ]ₓ`를 곱한다. 우리는 생략했다. `δθ`가 매우 작아 2차
> 효과이고, 많은 구현이 같은 선택을 한다. 정밀도가 문제 될 때 재검토.

### 관측 5종

각 관측은 **둘로 나뉘어 있다**:

- `model_*()` — **부작용 없이** `(z, h, H, R)`만 반환. 순수 수학.
- `update_*()` — 게이트를 걸고 `_ekf_update()`를 호출.

> **왜 나눴나.** `model_*`가 순수 함수라서 `test_filter.py`가 상태를
> 흔들어보며 `H`를 검증할 수 있다. 나누기 전에는 `H`를 볼 방법이 없었고,
> 그래서 중력 업데이트의 부호 오류가 살아남았다.

| 함수 | `H` | 이론 |
|---|---|---|
| `model_wheel_velocity` | `[0, Rᵀ[0,:], skew(v_body)[0,:], 0, 0]` | [01 §8.1](01_이론_오도메트리와_ESKF.md) |
| `model_gravity` | `[0, 0, skew(g_body), 0, **+I**]` | [01 §8.4](01_이론_오도메트리와_ESKF.md) |
| `model_nhc` | y·z 두 행 | [01 §8.2](01_이론_오도메트리와_ESKF.md) |
| `model_zupt` | `[0, I, 0, 0, 0]` | [01 §8.3](01_이론_오도메트리와_ESKF.md) |
| `model_zaru` | `[0, 0, 0, I, 0]` | [01 §8.5](01_이론_오도메트리와_ESKF.md) |

**`update_gravity()`의 게이트 두 개**는 `model_`이 아니라 여기 있다.
호출자가 잊을 수 없게 하려는 의도다. 특히 요레이트 게이트가 없으면
원심력을 기울기로 오인해 방위가 망가진다 (원 궤적 시험 −48.3° → +0.17°).

## `odometry.py` — 시스템의 중심

네 가지가 들어 있다.

**1. 바퀴 → 바디 운동** (`wheel_speeds_mps`, `body_velocity`)
`WHEEL_SIGN`과 `WHEEL_RADIUS_M`을 적용하는 유일한 곳.

> 여기에 **바퀴 기반 yaw rate는 일부러 없다.** 차동구동 공식
> `(v_R − v_L)/트랙`은 스키드스티어에서 낙관적이다(바퀴가 옆으로 긁힌다).
> 이 파일의 모든 yaw rate는 **바이어스 보정된 자이로**에서 온다
> ([01 §3.3](01_이론_오도메트리와_ESKF.md)).

**2. `StillnessDetector`** — [01 §8.6](01_이론_오도메트리와_ESKF.md)의 네 조건.
핵심은 **표준편차** 검사다.

```python
gyro_std = np.std(np.array(self.gyro_window), axis=0).max()
if gyro_std > config.ZUPT_GYRO_STD_MAX:
    return False        # the load-bearing test
```

`|gyro| < 임계값`이 실기에서 **2000 사이클 중 0회** 발동한 이유와,
"바이어스 보정 크기" 검사를 넣었다가 **1981개 중 1960개를 기각**했던
경위가 클래스 docstring에 있다. 지우지 말 것 — 같은 함정을 두 번 판 기록이다.

**3. `Odometry.step()` — 갱신 순서.**

```
body-frame sensor input → stillness detector
→ startup alignment (until ready; prediction/updates skipped)
→ predict → (ZUPT+ZARU) or (wheel+NHC) → gravity → continuous pose integration
```

> ### 이 파일이 존재하는 이유
>
> 이 순서가 **다섯 곳에 복사되어 있었다** — 실기 루프, 조종 루프, 재생 도구,
> 시뮬 테스트, GUI 튜너. 테스트에는 `keep them in sync`라는 주석까지
> 붙어 있었다.
>
> 서로 어긋나는 날, **재생 결과가 로버가 실제로 한 일과 달라진다.**
> 그러면 로그로 내린 튜닝 결정이 전부 틀리는데, 아무것도 그걸 알려주지
> 않는다. 그래서 사본은 하나뿐이고 나머지는 전부 이걸 부른다.

두 분기가 배타적인 것도 의도다. 정지 중엔 바퀴 속도가 어차피 0이라
NHC가 더할 게 없고, 둘 다 돌리면 "안 움직인다"는 같은 증거를 두 번 세게 된다.

**4. 공개 pose와 내부 `state['p']`의 분리.**

```
Odometry.position      = p_odom += R(q_ESKF)[v_wheel,0,0]dt
Odometry.inertial_position = state['p']  # 진단 전용
```

2026-09-06 로그에서 내부 `p`를 그대로 화면에 표시했을 때 ZUPT 한 cycle이 위치를
최대 4.0 cm 바꾸고, gravity/wheel cross-correction이 직선 `y`를 10 cm 이상 옮겼다.
위치 관측이 없는 시스템에서 이 값을 실제 차량 pose처럼 공개한 것이 문제였다.
replay와 live panel의 파란 선은 연속 `p_odom`, 자주색 점선은 내부 `state['p']`다.

## Replay의 `Filter cycle` — 한 cycle을 완전히 해부하기

`replay_gui.py`는 별도 디버그 수식을 계산하지 않는다. 실제 `Odometry.step()`과
`_ekf_update()`가 선택적으로 남긴 trace를 표시한다. 따라서 이 표의 숫자는
실제 상태에 더해진 숫자다. tracing을 켠 필터와 끈 필터가 bit-for-bit 같은지는
`test_filter.py`의 `trace is read-only` 검사가 보장한다.

### 실행 순서

| 순서 | 단계 | 입력 | 상태에 하는 일 |
|---:|---|---|---|
| 1 | 정지 판정 + 초기 정렬 gate | 휠 속도, gyro/accel 표준편차, `||a||−g` | 정렬 중이면 평균 수집 후 return |
| 2 | `predict` (정렬 완료 후) | raw gyro, raw accel, `dt` | `p,v,q` 적분, `P ← FPFᵀ+Q` |
| 3a | `wheel` | 평균 전진 휠 속도 | 이동 중 body `v_x` 보정 |
| 3b | `nhc` | `v_y^body=0`, `v_z^body=0` | 이동 중 횡·수직 속도 보정 |
| 3c | `zupt` | world `v=0` | 정지 중 속도 보정 |
| 3d | `zaru` | true angular rate `=0` | 정지 중 gyro bias 보정 |
| 4 | `gravity` | accelerometer gravity direction | gate 통과 시 roll/pitch·bias 보정 |
| 5 | pose 출력 | wheel forward speed + ESKF `q` | `p_odom += R(q)[v_wheel,0,0]dt` |

3a/3b와 3c/3d는 동시에 실행되지 않는다. 탭에 `SKIPPED`가 보이면 계산 실패가
아니라 선택되지 않은 정상 분기이며, 이유가 함께 표시된다.

### Update 탭의 열

관측 update는 모두 같은 순서다.

```
y = z - h
S = H P H^T + R
K = P H^T S^-1
delta_x = K y
P = (I-KH) P (I-KH)^T + K R K^T
nominal_state <- nominal_state (+) delta_x
```

| GUI 값 | 정확한 뜻 |
|---|---|
| `z measurement` | 센서 또는 constraint가 실제로 준 값 |
| `h predicted` | 현재 상태가 예측한 같은 물리량 |
| `y = z-h` | innovation. 측정과 예측의 차이 |
| `sqrt diag(R)` | 측정 모델이 선언한 1-sigma 잡음 |
| `sqrt diag(S)` | 상태 불확실성까지 포함한 innovation 1-sigma |
| `NIS` | `yᵀS⁻¹y`. innovation이 선언한 불확실성과 맞는지 |
| `delta p ... delta ba` | **`K y` 15개 전부. 실제 주입할 error state** |
| `State effect` | 전후 `p,v,q,RPY,bg,ba` 차이. `delta theta`와 Euler RPY 차이는 같지 않을 수 있음 |
| `sigma ...` | `sqrt(diag(P))`. 각 error state의 1-sigma |

`H`, `R`, `S`, `K`, `P before/after`는 접힌 행렬을 펼치면 모두 볼 수 있다.
Predict 탭은 `gyro-bg`, `accel-ba`, world acceleration, 회전 증가량과
`F`, `Q`, `P before/after`를 같은 방식으로 보여준다.
그 아래 `Reported pose step`은 같은 raw cycle의 `v_wheel`, `v_world`, `delta p`,
누적 `p_odom`을 보여준다. 따라서 내부 update와 실제 출력에 더해진 값을 구분할 수 있다.

방위 관측이 없는 `wheel/NHC/ZUPT/gravity`에는 한 단계가 더 있다. local error의
world 수직축은 `n = R(q)^T[0,0,1]`이고, 이 축 회전이 global yaw다.

```
C_theta = I - n n^T
K_constrained = C K
```

실제 correction과 Joseph covariance update 모두 `K_constrained`를 사용한다.
quaternion의 유한회전에서 생기는 2차 yaw 변화도 마지막에 정확히 복원한다.
GUI의 `K_unconstrained`와 `K`를 비교하면 제거된 성분을 볼 수 있다. `predict`와
ZARU는 이 제한을 받지 않는다. 전자는 실제 회전이고, 후자는 정지에서 배운 bias가
이전 상대회전 오차를 고치는 경로이기 때문이다.

### Yaw 원인 읽기

`cumulative yaw attribution`은 원본 **100 Hz 모든 cycle**의 단계별 실제 Euler-yaw
변화를 누적한다. GUI 표시 자체는 20 Hz지만 중간 80 Hz를 버려 합산하지 않는다.
Starting from zero yaw, the accumulated stage changes equal the unwrapped
yaw change. The displayed Euler yaw agrees only modulo 360 degrees:

```
displayed ESKF yaw = wrap180(predict + wheel + nhc + zupt + zaru + gravity)
```

- `predict` 변화: 주로 `(gyro_z-bg_z)dt` 적분이다.
- `zaru` 변화: 정지 후 새로 배운 bias로 과거 자세 오차를 보정한 효과다.
- `wheel/NHC/ZUPT/gravity`의 누적 yaw는 현재 구현에서 항상 수치상 0이어야 한다.
- `predict`는 `(gyro-bg)dt`, `zaru`는 정지 bias 재추정에 따른 상대 yaw correction이다.

`23:47` 로그에서 수정 전후 귀속은 다음과 같다.

| | predict | wheel | NHC | ZUPT | ZARU | gravity | 합계 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 수정 전 | −6.89° | +12.12° | −8.89° | +0.41° | +3.00° | +5.39° | +5.14° |
| 현재 | −0.312° | 0° | 0° | 0° | +0.384° | 0° | **+0.072°** |

현재는 시작 5초 정지 평균으로 `bg`, roll, pitch를 초기화하고 그때의 정면을
yaw 0°로 정의한다. 이 동안 `teleop.py`는 모터에 0만 보낸다. 정렬시간을 2/3/5/8초로
바꾼 민감도 검사에서도 최종 yaw는 0.249/0.134/0.072/0.069°로 같은 결론이었다.
따라서 특정 5초 값으로 직진 로그를 맞춘 결과가 아니다.

## `teleop.py` — 조종 루프

한 사이클:

```
1. 조이스틱 값 확정 (deadman + 정렬 중 0 강제)   ← 센서 읽기보다 먼저
2. 바퀴 Sync Read + IMU 읽기
3. 시작 5초면 alignment, 이후 eskf.predict() → update_*()
4. 로깅
5. dxl_control.drive()
6. 패널 전송 (15 Hz) + pygame 창
7. pace()  ← 박자 유지
```

### 여기 박혀 있는 세 가지 안전 장치

These are existing protections, not a complete fault-handling guarantee.
See [10 — control and sensor issues](10_code_review.md) for write failures,
blocking reads, and startup/cleanup gaps still requiring changes.

**1. 순서.** 조이스틱을 **1번**에서 확정한다. 그래야 2번이 실패해도
5번이 올바른 값을 보낸다.

**2. 읽기 실패가 쓰기를 막지 않는다.** Goal Velocity는 모터에 **래치**된다.
`if data is None: continue`로 두면 버스가 죽었을 때 `drive()`가 영영
호출되지 않고 **deadman까지 같이 죽어** 바퀴가 마지막 속도로 계속 돈다.
지금은 실패 경로에서도 명령을 보내고, 50사이클 연속 실패하면 조이스틱과
무관하게 정지시킨다.

**3. `pace()`를 어느 경로도 건너뛰지 않는다.** 예전에 `continue`가
`next_tick += dt`를 건너뛰어 루프가 따라잡으려 폭주했다 (지터 2.20 ms,
최대 갭 45 ms). 지금은 0.28 ms.

### 포트 점검

`socketio.run()`은 데몬 스레드에서 돈다. 5000번 포트가 이미 잡혀 있으면
**그 스레드만 죽고 메인 루프는 멀쩡히 계속 돈다.** 폰은 *다른* 프로세스에
접속하고, 모터를 쥔 이쪽은 명령을 영영 못 받는다. 증상이 "토크 ON, 100 Hz,
에러 없음, 그런데 안 움직임"이라 원인과 전혀 안 닮았다.
그래서 시작할 때 검사하고 **바로 멈춘다.**

## `live_panel.py` — 실시간 패널

폰 조이스틱과 **같은 서버·같은 소켓**을 쓴다. 추가 프로세스도 의존성도 없다.

```
폰     http://<IP>:5000        조이스틱
노트북 http://<IP>:5000/panel  패널
```

- 필터는 100 Hz, 패널 전송은 **15 Hz** — 브라우저가 병목이 되면 안 된다
- 궤적은 100 ms마다 한 점만 (1시간이면 36만 점이 된다)
- **NIS 카드**가 핵심: `replay.py`와 같은 지표를 3초 이동평균으로
  띄운다. 나쁜 런을 10초 안에 끊을 수 있다

`--headless`를 주면 pygame 창 없이 패널만 쓴다 (노트북을 로버에 올린 채
뚜껑 덮고 주행할 때).

## `replay_gui.py` — 실주행 재생과 기준점 비교

COM 포트를 열지 않는 읽기 전용 로컬 웹 도구다. CSV의 원본 샘플은 전부
`Odometry.step()`에 넣어 100 Hz 그대로 계산하고, 브라우저로 보낼 표시 프레임만
20 Hz로 줄인다. 따라서 GUI가 보여주는 필터와 실기/CLI 재생 필터는 같은 코드다.

```
CSV 전체 샘플 ─► Odometry.step() ─► ESKF 상태·NIS
                                      │
                                      ├─► 20 Hz 표시 프레임 ─► 시간 재생
줄자 정지점 ─► 장시간 정지로 구간 매칭 ─┴─► 체크포인트 오차
```

`2334`, `2347` 로그에는 사용자가 실제로 측정한 체크포인트만 등록돼 있다.
연속 실제 위치는 측정하지 않았으므로 임의의 “true trajectory”를 만들지 않는다.
지도는 추정 궤적과 기준선을 겹치고, 표는 정지점에서만 실제/추정 `x,y`와
2D 오차를 계산한다. 시험별 값은 코드가 아니라
[`logs/experiments.json`](../logs/experiments.json)에 둔다.
