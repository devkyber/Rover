## 2. 데이터가 제대로 들어오는지 확인 ★

**로그를 믿기 전에 반드시 이걸 먼저 돌린다.**

```bash
python test_pipeline.py                 # 모터 + IMU
python test_pipeline.py --fake-motors   # IMU만
python test_pipeline.py --fake          # 하드웨어 없이
```

읽기 → 로깅 → 재생 전 구간을 몇 초 돌린 뒤 **자동으로 감사**한다.
숫자를 출력하고 "괜찮아 보이네" 하는 게 아니라 항목별로 PASS/FAIL을 찍는다.

```
[PASS] loop rate                   100.0 Hz over 600 samples
[PASS] host timestamps increasing  min gap 7.79 ms, max 12.34 ms
[PASS] loop jitter < 3 ms          std 0.26 ms
[PASS] IMU clock increasing        min 9.17 ms, max 19.36 ms
[PASS] accel magnitude ~ 1 g       mean 9.770 m/s^2
[PASS] all wheels every cycle      expected 2, min seen 2
[PASS] no dropped motor packets    0 cycles dropped
[PASS] replay values match log     worst difference 5.00e-07
N/N checks passed
```

**제일 중요한 항목은 마지막 `replay values match log`다.** CSV에 쓴 값이 다시 읽었을 때
그대로 나오는지 확인한다. 이게 통과해야 로그를 보관할 가치가 있다.

이때 같이 출력되는 **정지 시 자이로 바이어스**를 봐 둘 것:

```
gyro bias at rest  [ 0.0304 -0.0654 -0.0357] rad/s ([ 1.74 -3.75 -2.05] deg/s)
```

LSM6DS3는 바이어스가 크다. 이 값이 ZUPT/ZARU 임계값을 정하는 근거가 된다.

## 3. 주행하며 로그 남기기

```bash
python teleop.py --tag drive
```

**로그 이름은 자동이다** — `logs/2026-09-06_1432_drive.csv`처럼 날짜·시각·태그로
만들어진다. 고정 이름을 쓰면 다음 실험이 이전 실험을 **조용히 덮어쓰고**, 며칠 뒤
그 로그로 다시 튜닝하려 할 때야 없어진 걸 알게 된다. `--tag`는 이름 조각만 바꾸고,
`--log <경로>`로 직접 지정할 수도 있으며, `--no-log`면 안 남긴다.

출력되는 `http://<IP>:5000`을 **폰으로 접속**. 왼쪽 스틱 = 전후, 오른쪽 스틱 = 회전.
매 사이클 `읽기 → ESKF → 로깅 → 속도 전송`이 돌고, 화면에 위치·자세·ZUPT 상태가 실시간으로 뜬다.

실행 직후 로버를 평평한 바닥에서 **연속 5초간 건드리지 않는다.** 패널의 motion이
`ALIGNING 0% → 100%`로 진행된다. 이 동안 코드는 joystick 값을 무시하고 모터에
0만 보낸다. 평균 gyro를 초기 bias로, 평균 중력방향을 roll/pitch로 쓰고, 완료 순간
로버의 정면을 local-world yaw 0°로 정의한다. `moving` 또는 `STOPPED (ZUPT)`로
바뀐 뒤에만 출발한다. 중간에 움직이면 정렬 표본은 버려지고 0%부터 다시 시작한다.

**처음 돌릴 때 반드시 확인할 것 — 바퀴 회전 방향.**
바퀴를 띄우거나 로버를 고정한 상태에서 왼쪽 스틱을 앞으로 밀었을 때
**모든 바퀴가 전진 방향으로** 돌아야 한다. 하나라도 반대면 `config.py`의
`WHEELS` 표에서 그 줄의 side 글자(`"L"`/`"R"`)를 뒤집는다.
**모터의 Drive Mode(10) Reverse 비트는 건드리지 않는다 — 소프트웨어와 상쇄된다.**

안전장치: 폰에서 0.5초간 신호가 없으면 바퀴가 자동으로 멈춘다(deadman).
버스 응답이 0.5초간 끊겨도 마찬가지로 멈춘다 (§3-1).

### 3-1. 라이브 패널 ★

```
폰    http://<IP>:5000        조이스틱
노트북 http://<IP>:5000/panel  라이브 패널
```

**같은 서버, 같은 소켓이다.** 추가 프로세스도, 추가 의존성도 없다.
폰으로 조종하면서 노트북 브라우저로 패널을 동시에 띄우면 된다.
노트북을 로버에 올린 채 뚜껑을 덮고 돌리려면 `--headless`를 붙여
pygame 창을 아예 없애고 패널만 쓴다.

```bash
python teleop.py --tag drive --headless
```

패널이 보여주는 것:

| 카드 | 무엇을 보나 |
|---|---|
| **status** | `ALIGNING` 진행률, 링크 상태, ZUPT 여부, 실제 루프 Hz, 드롭 수 |
| **estimate** | pos / vel / rpy / 자이로 바이어스 현재값 |
| **consistency (NIS)** | 최근 3초 평균 NIS와 `ratio = mean/target` ★ |
| **path** | 위에서 본 궤적 (등축 — 정사각 주행은 정사각으로 보여야 한다) |
| **velocity / attitude** | 스트립 차트 |
| **gyro bias** | 수렴 후 **평평해져야** 한다. 계속 움직이면 ZARU가 못 잡고 있는 것 |
| **wheel speed** | 바퀴 4개 실측 속도 — 방향 확인에 바로 쓴다 |

**NIS 카드가 핵심이다.** `replay.py`가 사후에 계산하는 것과 같은
지표를 이동 평균으로 실시간 표시한다. `config.py`에서 R을 바꾸고 다시
띄우면 그 효과를 주행 중에 바로 볼 수 있다. 나쁜 런을 10초 안에
알아채고 끊을 수 있다는 게 로그를 나중에 열어보는 것과의 차이다.

패널은 필터 상태를 **보여주기만** 한다. 조종은 폰이 하고, 로그는
자동 이름으로 남는다. 패널을 열지 않아도 주행과 로깅은 그대로 돌아간다.

### 어떤 로그를 찍어야 하나

| 목적 | 주행 방법 |
|---|---|
| **ZUPT/ZARU 검증** | 그냥 20초 가만히 둔다 (정답을 아는 유일한 케이스) |
| **바퀴/NHC 튜닝** | 직진 → 정지 → 직진, 회전 섞어서 30초 이상 |
| **드리프트 측정** | 테이프로 정사각형 그려놓고 출발점으로 되돌아오기 |

마지막 방법이 실전 표준이다. 출발점 = 도착점이므로 **최종 위치 오차가 곧 드리프트**다.

## 4. 로그 검사와 필터 검증 ★★

### 4-0. 차량 움직임을 재생한다

```bash
python replay_gui.py
```

브라우저가 `http://127.0.0.1:5001`로 열린다. 모터와 IMU는 연결하지 않아도
되고, 이 프로그램은 COM 포트나 모터를 열지 않는다.

- 로그 선택 후 `Load`: 원본 100 Hz 전부를 실제 `Odometry.step()`으로 다시 계산
- `Play/Pause`, `Step`, 타임라인, `0.25x~10x`: 로그 시각에 맞춘 재생
- 지도: 파란 ESKF 궤적, 현재 로버 위치와 yaw
- 신호: 바퀴 속도, 자세, 자이로와 같은 시각의 세로 커서
- yaw attribution: `predict/ZARU`가 yaw에 누적한 양. wheel/NHC/ZUPT/gravity는 0이어야 함
- NIS: 현재 시점까지의 최근 관측 일관성
- `Filter cycle`: 단계 탭에서 `z,h,y,R,S,NIS,K·y`, 상태 변화와 전체 행렬 확인
- 줄자 기준이 있는 `2334`/`2347`: 체크포인트 행을 누르면 해당 정지 시점으로 이동

**정답의 범위를 과장하지 않는다.** 이 두 로그에서 줄자로 잰 것은 정지점의
종방향 거리뿐이다. GUI의 `true x/y` 중 `x`는 실측값이고, `y=0`은 실제 횡방향을
외부 센서로 잰 값이 아니라 “기준 직선을 따라갔다”는 가정이다.
정지점 사이의 연속 실제 궤적은 모션캡처나 상부 카메라 같은 외부 기준 없이는 모른다.

새 로그의 실측점은 [`logs/experiments.json`](../logs/experiments.json)에
`[[x,y], ...]`로 추가한다. 각 점에서 1초 이상 멈추면 자동으로 매칭된다.

특정 로그를 바로 열 수도 있다.

```bash
python replay_gui.py ../logs/2026-09-06_2347_drive.csv
```

원인 분석은 timeline을 문제 시각으로 옮긴 뒤 `predict`, `wheel`, `nhc`,
`zupt`, `zaru`, `gravity` 탭을 차례로 누른다. `State effect`는 그 단계가
명목상태에 실제로 만든 변화이고, `delta ...`는 `K·y`로 계산된 15-state
correction이다. 각 열과 행렬의 정의는 [02 Filter cycle](02_구현_코드해설.md#replay의-filter-cycle--한-cycle을-완전히-해부하기)에 있다.

GUI는 관찰과 구간 선택에 쓰고, 재현 가능한 숫자 보고서와 PNG는 아래 CLI를 쓴다.

```bash
python replay.py ../logs/2026-09-06_1432_drive.csv --plot ../data/2026-09-06_1432_drive.png
```

**로그는 `logs/`, 그림은 `data/`에 둔다.** 로그는 실험을 다시 해야만 얻을 수 있는
입력이고, 그림은 언제든 다시 만들 수 있는 산출물이다. 지워도 되는 것과 절대
지우면 안 되는 것이 폴더 이름만으로 갈린다.

세 가지를 한 번에 한다.

### 4-1. 로그 자체 검사

```
samples        2000
duration       19.99 s
rate           100.0 Hz  (gap min 8.98 / max 11.05 ms)
|accel|        mean 9.764, std 0.020 m/s^2   (still = 9.81)
wheel ID 1     |vel| max 0.000 rad/s, moving 0.0% of the time
```

루프가 멈춘 구간, IMU 샘플 재사용, 바퀴가 실제로 돌았는지를 먼저 본다.
**여기가 이상하면 필터 결과는 볼 필요가 없다.**

### 4-2. 필터를 통과시킨 결과

```
final position [-0.  0. -0.001] m
final rpy      [-1.04 -0.33 -0.03] deg
gyro bias      [ 0.03065 -0.06536 -0.03623] rad/s
ZUPT active    1972/2000 cycles (98.6%)

Log is stationary throughout, so final position IS the
drift: 0.0008 m  [GOOD]
```

정지 로그라면 **출발점 = 정답**이므로 최종 위치가 곧 드리프트다. 이게 유일한 공짜 정답이다.

`--plot`을 주면 경로·속도·자세·**자이로 바이어스 수렴**을 PNG로 뽑는다.
바이어스 그래프가 초반에 값을 잡고 그 뒤로 평평해야 정상이다.

### 4-3. NIS — 정답 없이 필터를 판정하기

**이게 핵심이다.** 실제 주행에는 정답이 없다. 그래서 다른 걸 본다.

> **NIS(Normalized Innovation Squared)** 는 이렇게 묻는다:
> *"필터가 측정값을 예측했다가 틀렸을 때, 자기가 틀릴 거라고 말한 만큼 틀렸는가?"*
>
> 필터 자신의 숫자만 쓰므로 **정답이 필요 없다 → 실제 주행 로그에 그대로 쓸 수 있다.**

관측 종류별로 mean NIS가 **그 관측이 주는 값의 개수**에 가까워야 한다
(바퀴속도 1개, NHC 2개, ZUPT/ZARU/중력 3개).

```
observation       n   mean NIS   target   verdict
gravity        2000      0.163        3   too timid - lower R_GRAVITY
zaru           1972      6.235        3   ok
zupt           1972      0.777        3   too timid - lower R_ZUPT
```

| NIS가 | 뜻 | 조치 |
|---|---|---|
| 목표보다 **훨씬 크다** | **과신**. 필터가 자기 불확실성을 실제보다 작게 봄 | 해당 **R을 키운다** |
| 목표보다 **훨씬 작다** | **너무 소심**. 믿어도 될 측정을 버리고 있음 | 해당 **R을 줄인다** |
| 목표 근처 | 정직함 | 그대로 둔다 |

> ⚠️ **정지 로그에서는 `zupt`/`zaru`/`gravity` 판정만 의미가 있다.**
> 로버가 서 있으면 바퀴·NHC의 innovation이 당연히 0에 가까워서 항상
> "too timid"로 나온다. 그건 **주행 로그로 튜닝해야 한다.** 도구가 알아서 경고해 준다.

## 5. 튜닝 루프 — 실제로 이렇게 했다

`config.py`의 R 값 7개가 튜닝 대상이다. **한 번에 하나씩만 고친다.**

`R`이 지배적인 구간에서는 `R`을 키우면 대체로 NIS가 내려가므로
`sqrt(현재 NIS/목표)`는 **첫 후보를 만드는 근사값**으로 쓸 수 있다.
하지만 상태와 공분산이 다음 시각으로 이어지므로 전체 재생의 NIS는 `R`에 대해
단조가 아니며 U자형이 될 수 있다. 반드시 후보의 양쪽도 같은 로그로 다시 재생한다.

### 실제 사례: R_ZARU

**1단계 — 문제 발견.** 정지 20초 로그를 replay:

```
zaru  1972   1746.863   3   OVERCONFIDENT - raise R_ZARU (582.3x too sure)
```

`R_ZARU = 0.0001`은 그냥 감으로 잡은 값이었다. LSM6DS3 자이로는 그보다 훨씬 시끄럽다.

**2단계 — 첫 후보.** NIS 비율의 제곱근으로 `R × √582 ≈ R × 24`를 시험한다.

```python
R_ZARU = 0.0001  →  0.0024
```

**3단계 — 재검증.** 같은 로그를 다시 replay:

```
zaru  1972   6.235   3   ok
```

1747 → 6.2. **로그를 다시 찍을 필요가 없다.** 같은 파일을 다시 돌리면 된다.
이게 오프라인 튜닝의 장점이다.

현재 상수들은 실측 로그에서 출발했지만, 5초 정렬과 yaw 보존이라는 모델 변경 후
**다시 검증 중**이다. 저속 `23:47`에서는 wheel/NHC/ZUPT가 일관적이지만 freestyle
로그에서는 wheel/NHC/gravity NIS가 크다. 한 상수를 다시 맞추기보다 회전·slip에
따른 adaptive R과 wheel yaw-rate를 외부 정답으로 검증해야 한다.

## 6. 문제 해결

| 증상 | 원인 |
|---|---|
| `Access is denied` | DYNAMIXEL Wizard가 포트를 잡고 있다 |
| Wizard는 되는데 파이썬만 응답 0 | **4.5 Mbps SDK 함정** — [`vendor/PATCHES.md`](../rover/vendor/PATCHES.md) |
| `No IMU data on COM25` | 스케치 미업로드, 또는 baud 불일치 (`IMU_BAUD` vs `SERIAL_BAUD`) |
| 바퀴가 안 돎, 패널은 정상 | **teleop.py가 두 개 떠 있다** — 아래 참고 |
| 바퀴가 안 돎 | Operating Mode가 3(Position). `dxl_tool.py`로 확인 |
| 바퀴가 반대로 돎 | `config.py`의 `WHEELS` 표에서 side 글자를 뒤집는다 |
| `ZUPT active 0%` | 정지 감지 임계값. [8장](#8-이-과정에서-실제로-찾은-버그) 참고 |
| 정지인데 yaw가 표류 | 위와 같은 원인. ZUPT가 안 걸리면 ZARU도 안 걸린다 |
| 루프가 100 Hz 안 나옴 | Windows Latency Timer를 1 ms로 |

### teleop.py가 두 개 떠 있을 때 ★

**증상이 아주 헷갈린다.** 폰 조이스틱은 정상으로 보이고, 터미널은
`torque ON`에 100 Hz를 찍고, 에러도 없는데, **바퀴만 안 돈다.**

원인: 5000번 포트를 먼저 잡은 쪽이 웹 서버가 된다. 나중에 뜬 쪽은
`socketio.run()`이 데몬 스레드 안에서 죽는데, 메인 루프는 그대로
돌아간다. 그래서 폰이 접속하는 건 **다른 프로세스**이고, 조이스틱
명령도 그쪽으로 간다. 모터를 쥐고 있는 이쪽은 명령을 영영 못 받아서
deadman이 계속 0을 보낸다.

지금은 시작할 때 포트를 검사해서 **바로 멈춘다**:

```
Port 5000 is already in use -- another teleop.py is still
running. The phone would talk to THAT one, not to this.
```

떠 있는 걸 다 정리하고 다시 실행한다:

```bash
taskkill /F /IM python.exe
```

확인하려면:

```bash
powershell "Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -like '*teleop*' } | Select ProcessId,CommandLine"
```

### IMU 스케치를 다시 올려야 할 때

```bash
"C:\Program Files\Arduino CLI\arduino-cli.exe" compile --fqbn arduino:samd:nano_33_iot ../arduino/imu_stream
"C:\Program Files\Arduino CLI\arduino-cli.exe" upload -p COM25 --fqbn arduino:samd:nano_33_iot ../arduino/imu_stream
```
