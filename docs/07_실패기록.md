# 실패 기록 (Failure Register)

> **이 리포에서 실제로 깨졌던 모든 것.** 다른 문서에는 결론만 적고,
> 사건은 여기에만 적는다. 한 사건 = 한 항목 = 하나의 ID.

이 문서가 따로 있는 이유는 두 가지다.

1. **이론 문서를 깨끗하게 유지한다.** 01–06은 "지금 시스템이 무엇인가"만
   말한다. "왜 저렇게 안 했는가"는 전부 여기로 온다.
2. **증상이 원인과 안 닮았던 사례를 모은다.** 아래 등록 사례 중 절반은
   증상만 보고는 원인을 찾을 수 없는 것들이었다. 비슷한 증상이 다시
   나오면 여기부터 본다.

### 항목 추가 규칙

```
### F-nn  한 줄 제목
**증상**       무엇이 보였나 — 반드시 숫자로
**원인**       진짜 원인. 증상과 다르면 그 차이를 명시
**조치**       무엇을 바꿨나 (파일 이름)
**재발 방지**  이 실수를 다시 쓸 수 없게 만든 장치. 없으면 "없음"이라 적는다
```

`재발 방지`가 "없음"인 항목은 **다시 일어날 수 있다는 뜻**이다.
문서 끝에 그 목록만 따로 모아두었다.

# A. 필터 수학

공통점: **성능 지표가 멀쩡해 보여도 틀려 있을 수 있다.**
그래서 `test_filter.py`는 성능보다 **수식 자체**를 먼저 검사한다.

<a id="f-01"></a>
### F-01  가속도계 부호 컨벤션

**증상** 직진 시나리오에서 위치가 23 m로 발산.
**원인** 평평하게 놓인 IMU는 중력을 **누르는 반력**을 재므로 `[0,0,+g]`가 맞는데
`[0,0,−g]`로 가정했다. 부호 하나가 중력을 두 배로 만든다.
**조치** `update_gravity()`의 예측 측정값과 시뮬 데이터를 함께 수정.
**재발 방지** 시나리오 테스트가 이 규모의 발산은 반드시 잡는다.

<a id="f-02"></a>
### F-02  `Q` 이산화를 `(σ·dt)²`로 썼다

**증상** 필터가 자기 자세를 과신해서 중력 업데이트가 기울기를 못 고침.
**원인** 잡음 밀도(per √Hz)를 dt 동안 적분하면 분산은 `σ²·dt`다.
`(σ·dt)²`는 dt = 0.01에서 **Q를 100배 작게** 만든다.

```python
Q[6:9, 6:9] = (GYRO_NOISE * dt) ** 2     # 틀림
Q[6:9, 6:9] = GYRO_NOISE ** 2 * dt       # 맞음
```

**조치** `eskf.predict()`.
**재발 방지** ❌ 없음. 유도는 [01 §7.4](01_이론_오도메트리와_ESKF.md)에만 있다.

<a id="f-03"></a>
### F-03  회전 중에 중력 업데이트를 그대로 돌렸다

**증상** 원 궤적 20초에서 yaw −48.3°.
**원인** 0.5 m/s로 0.3 rad/s 선회하면 구심가속도 0.15 m/s²가 **옆방향 비력**으로 잡힌다.
중력과 수직이라 `|a|`가 거의 안 변해서 기존 `| |a| − g | < 0.5` 게이트를 **그냥 통과**한다.
필터는 이걸 roll로 읽고, 그 가짜 roll이 공분산을 타고 yaw로 샌다.

| | 위치오차 | yaw 오차 |
|---|---|---|
| 게이트 없음 | 0.71 m | **−48.3°** |
| 중력 업데이트 끔 | 0.003 m | +0.17° |
| **yaw rate 게이트 추가** | **0.003 m** | **+0.17°** |

**조치** `config.GRAVITY_GATE_MAX_YAW_RATE = 0.1` rad/s.
**재발 방지** 게이트를 `update_gravity()` **안에** 넣었다. 호출하는 쪽이 깜빡할 수 없다.

<a id="f-04"></a>
### F-04  중력 야코비안의 `∂y/∂δba` 부호가 `−I`였다

이 리포에서 **가장 오래 살아남은 버그**이고, 잡힌 경위가 핵심이다.

**증상** 없음. 정지 로그에서 성능 차이가 사실상 0이었다.

```
H_ba = −I  (틀림)   drift 5.28 mm   ba = [−0.031, −0.009, −0.038]
H_ba = +I  (맞음)   drift 5.35 mm   ba = [−0.001, +0.006, −0.042]
```

**원인** 정지 상태에서 가속도계 바이어스는 기울기와 **원리적으로 구분되지 않는다**
([05 §1-4](05_한계와_로드맵.md)). 관측 불가능한 방향의 오류는 성능 지표에 나타나지 않는다.
**조치** `eskf.model_gravity()`. 문서를 쓰며 식을 다시 유도하다 발견했다 —
테스트가 아니라 **유도가 잡았다.**
**재발 방지** `test_filter.py` 1층이 모든 `H`를 수치미분과 대조한다.
다시 넣으면 정확히 그 블록을 지목한다:

```
[FAIL] gravity / tilt   max |H − H_numeric| = 2.00e+00
       row 0, dba block: analytic −1.0000 vs numeric +1.0000
```

> **교훈** 성능 테스트는 관측 가능한 방향만 검사한다.
> 관측 불가능한 방향을 검사하는 유일한 방법은 **수학을 직접 검사**하는 것이다.

<a id="f-05"></a>
### F-05  NIS가 `R`에 대해 단조라고 믿었다

**증상** 세 `R`을 함께 2.5배 줄였더니 발산 (zupt NIS 25, gravity 16).
**원인** 옛 주석은 "NIS가 1/R²로 스케일한다"고 적혀 있었다. 실제로는 **U자**다 —
`R`이 작으면 이득이 커져 상태가 흔들리고 innovation이 다시 커진다. 최솟값이 존재한다.
**조치** 주석을 실측 결과로 교체. **한 번에 하나씩** 바꾸는 좌표하강으로 전환.
**재발 방지** [03 §5.3](03_튜닝과_NIS.md)에 실측 U자 곡선을 남겼다.

<a id="f-06"></a>
### F-06  필터 수식을 고치고 재튜닝을 안 했다

**증상** F-04를 고치자 NIS가 통째로 이동 (gravity 2.40 → 2.16, zupt 2.58 → 1.75).
**원인** `R`은 **그 모델에 대해** 맞춰진 값이다. 모델이 바뀌면 무효다.
**조치** 좌표하강 재실행. 현재 값은 전부 F-04 수정 **이후**에 잡은 것이다.
**재발 방지** `config.py` 주석에 "모델이 바뀌면 재튜닝"을 박아두었다.

# B. 소프트웨어 구조

공통점: **한 줄의 제어 흐름이 안전장치를 통째로 무력화**시켰다.

<a id="f-07"></a>
### F-07  정지 판정을 `|gyro| < 임계값`으로 했다

영향이 가장 컸던 버그다.

**증상** 로버를 책상에 20초 가만히 뒀는데:

```
|gyro| 평균     0.0807 rad/s     (임계값 0.02)
gyro 축별 std   [0.0036, 0.0016, 0.0012] rad/s
정지 감지       0 / 2000 사이클
yaw 드리프트    20초에 −31.2°
```

std가 증명하듯 로버는 **완벽하게 정지**해 있었다.
**원인** LSM6DS3의 자이로 **바이어스**가 0.08 rad/s(4.6°/s)라 원시 크기가 임계값의 4배였다.
게다가 이건 **교착**이다 — 바이어스를 없애려면 ZARU가 돌아야 하고, ZARU는 자이로가
작아 보여야 돌고, 작아 보이려면 바이어스가 없어야 한다.
**조치** 질문을 바꿨다. "속도가 0에 가까운가?"가 아니라 **"속도가 변하고 있는가?"**
정지한 자이로는 *일정하게 틀린* 값을 읽는다. 짧은 창의 **표준편차**가 그걸 보고,
바이어스에 전혀 영향받지 않는다.

**결과: yaw 드리프트 −31.2° → −0.03°, ZUPT 98.6 % 작동, 위치 드리프트 0.8 mm.**

**재발 방지** `odometry.StillnessDetector`의 docstring이 이 사건 전체를 담고 있다.

<a id="f-08"></a>
### F-08  고치면서 같은 함정을 다시 팠다

**증상** 바이어스 보정된 자이로로 크기 검사를 추가했더니 **1960/1981 사이클 차단.**
**원인** `bg`는 ZARU가 수렴하기 한참 전에 다른 업데이트(바퀴·NHC·중력)에서 이미
0이 아니게 된다. 그 검사가 **쓰레기 바이어스 값으로 켜져서** 정작 그걸 고칠 업데이트를 막았다.
**조치** 제거. 바퀴 검사 + std 검사면 충분하다 — 바퀴가 멈춘 채로 로버가 회전할 수는 없다.
**재발 방지** `StillnessDetector` docstring에 "이 검사를 추가하지 말 것"을 명시.

<a id="f-09"></a>
### F-09  읽기 실패가 모터 쓰기까지 건너뛰었다 ★안전★

**증상** 버스가 답을 안 하기 시작하면 **폰을 놓아도, 창을 닫아도 바퀴가 계속 돈다.**

```python
data = dxl_reader.read_wheels(reader)
if data is None:
    dropped += 1
    continue          # ← drive()까지 같이 건너뛴다
```

**원인** Goal Velocity는 모터 안에 **래치**된다. 다음 명령이 올 때까지 유지된다.
이 `continue`가 `drive()`를 영영 호출하지 않게 만들어 **deadman까지 같이 죽였다.**
**조치** 조이스틱 값을 센서 읽기보다 **먼저** 계산하고, 실패 경로에서도 `drive()`를 호출한다.
0.5초(50사이클) 연속 실패하면 조이스틱과 무관하게 정지 명령.
**재발 방지** `teleop.py` 루프 주석에 순서와 그 이유를 명시.

<a id="f-10"></a>
### F-10  드롭 시 페이싱까지 건너뛰어 루프가 폭주했다

**증상** 지터 2.20 ms, 최대 갭 45 ms.
**원인** 같은 `continue`가 `next_tick += dt`도 건너뛰어, 패킷 하나 놓치면 루프가
따라잡으려 자유주행했다. **한 번의 손실이 지터 폭발이 된다.**
**조치** 어느 경로에서도 박자를 놓치지 않도록 페이싱을 일원화. **지터 0.28 ms, 드롭 0.**
**재발 방지** `pace()` 한 곳으로 모음. `pygame.clock.tick()` 대신 monotonic 페이싱
(실측 95.5 Hz → 100.0 Hz).

<a id="f-11"></a>
### F-11  갱신 순서가 다섯 파일에 복제돼 있었다

**증상** 없음 — 이건 **앞으로 일어날 사고**를 미리 등록한 것이다.
**원인** `predict → 정지판정 → ZUPT/ZARU 또는 휠/NHC → 중력`이 실기 루프, 조종 루프,
재생 도구, 시뮬 테스트, GUI 튜너에 각각 손으로 복사돼 있었다. 테스트에는
`keep them in sync`라는 주석까지 있었다. 하나만 어긋나는 날 **재생 결과가 로버가 실제로
한 일과 달라지고**, 그 로그로 내린 튜닝 결정이 전부 틀리는데 아무것도 알려주지 않는다.
**조치** `odometry.Odometry.step()` 하나로 통합. 사본은 하나뿐이다.
**재발 방지** 파일 상단 docstring이 이유를 설명한다. `gui_tuner.py`는 삭제했다.

<a id="f-12"></a>
### F-12  `gyro`와 `accel`을 바꿔 넘겼다

**증상** `record.py --fake`가 2초에 **−9.99 m 자유낙하.**
**원인** 둘 다 평범한 3-벡터라 예외도 형상 오류도 없다. **조용히 틀린다.**
F-11을 고치는 과정에서 새로 들어간 버그다.
**조치** 인자 순서 수정.
**재발 방지** `step(self, wheels, *, gyro, accel, dt)` — **키워드 전용.**
이제 모든 호출부가 이름을 써야 해서 같은 실수를 *쓸 수가 없다.*

> 리팩터링은 버그를 옮기는 게 아니라 **새로 만든다.**
> 옮긴 뒤에는 반드시 끝에서 끝까지 한 번 돌려본다.

<a id="f-13"></a>
### F-13  좀비 teleop 프로세스가 포트 5000을 잡고 있었다

**증상** 폰 조이스틱을 밀어도 **모터가 전혀 안 돈다.** UI는 정상 동작.
**원인** 이전 테스트로 띄운 `teleop.py --no-motors` 3개가 아직 살아 있었다.

**조치** 좀비 종료.
**재발 방지** `check_port_free()`가 시작 전에 5000번을 찔러보고 점유돼 있으면
**크게 실패**한다. 조용한 실패를 시끄러운 실패로 바꿨다.

### F-15  벤더 SDK가 4.5 Mbps를 모른다 (반나절)

**증상** 모터가 **어떤 baud에서도 응답하지 않는다.** DYNAMIXEL Wizard는 멀쩡히 본다.

**조치** 벤더 사본 수정. 같이 고친 것: `openPort()`는 실패 시 False가 아니라
**pyserial 예외**를 던진다(Wizard가 포트를 잡고 있을 때).
**재발 방지** [`rover/vendor/PATCHES.md`](../rover/vendor/PATCHES.md).
**SDK를 새 버전으로 올리면 이 패치가 사라진다.**

<a id="f-16"></a>
### F-16  Present Position의 signed 변환을 빼먹었다

**증상** 뒤로 굴린 바퀴가 **−1.237 rad인데 +6,588,396 rad로** 읽혔다.
**원인** 전류·속도만 signed 변환하고 위치는 안 했다. Present Position은 Velocity 모드에서
멀티턴 누적이라 **signed int32**다. 2륜일 땐 우연히 전부 양수라 가려져 있었다.
**조치** `dxl_reader.py`.
**재발 방지** 4륜 브링업 감사에서 드러났다. **값의 범위를 눈으로 보는 절차**가 잡았다.

<a id="f-17"></a>
### F-17  SyncRead 부분 성공을 평균냈다

**증상** 없음 — 그래서 위험하다.
**원인** SDK 소스를 읽고 알아낸 세 가지:

1. `getData()`는 실패 시 **`0`을 리턴**한다. 0은 멀쩡한 값이기도 해서 구분이 안 된다.
2. `getData()`의 길이는 **1/2/4만** 유효. 다른 값은 조용히 0.
   `isAvailable(id, 126, 10)`은 범위검사만 하므로 **True를 준다.**
3. **모터 하나가 죽으면 SyncRead 전체가 죽는다.** `rxPacket()`이 첫 실패에서 return하고
   `last_result = False`로 두기 때문에 모든 ID의 `isAvailable()`이 False가 된다.

**조치** "3개만 받아서 평균"내던 코드를 **`None` 리턴(사이클 폐기)** 으로 변경.
**재발 방지** 부분 데이터는 데이터가 아니다 — `read_wheels()`는 전부 아니면 `None`.

> 덤: Sync Read는 요청만 1패킷이고 **응답은 ID별로 순차 수신**이다.
> 왕복시간이 모터 수에 비례한다. "4개가 공짜"가 아니다 (2륜 0.95 ms → 4륜 1.14 ms).

# D. 실험 방법론

공통점: **코드는 멀쩡한데 데이터가 결론을 지지하지 못했다.**
이쪽이 가장 비쌌다 — 잘못된 데이터로 내린 결정은 되돌리기 어렵다.

<a id="f-22"></a>
### F-22  공중에서 바퀴만 돌린 로그로 튜닝하려 했다

**증상** `run1.csv`(405초, 바퀴 18 % 구동)에서 필터가 최종 위치를 **0.428 m**로 냈다.
로버는 1 mm도 움직이지 않았다.
**원인** 버그가 아니다. 휠 속도 업데이트는 "바퀴가 돌면 로버가 간다"를 가정하고,
공중에서는 그 가정이 **거짓**이다. 가정 위반이지 결함이 아니다.
**조치** 이 로그로 확인된 것은 **배선·타이밍·부호·로깅이 살아있다**는 것까지로 한정.
**재발 방지** `replay.py`가 바퀴가 한 번도 안 돈 로그를 감지하면
"wheel/nhc 판정을 무시하라"고 출력한다.

<a id="f-23"></a>
### F-23  정지 로그로 `R_WHEEL_VELOCITY`를 맞추려 했다

**증상** `replay.py`가 "lower R_WHEEL (9.5x too loose)"라고 말한다.
**원인** 정지 로그에서 휠 관측은 83번뿐이고 **유효표본 `N_eff` = 3**이다.
표본 3개로는 아무것도 판정할 수 없다.
**조치** 그 말을 믿지 않는다. 휠·NHC 튜닝은 **바닥 주행 로그**를 기다린다.
**재발 방지** `replay.py`가 표본 수를 함께 출력하고, 바퀴가 안 돈 로그에 경고를 붙인다.

<a id="f-24"></a>
### F-24  단일 시드 결과를 성능으로 착각했다

**증상** "stop and go" 시나리오가 한 시드에서 **0.577 m**, 10시드 최악은 **1.498 m.**
2.6배 차이.
**원인** 난수 하나에 과적합. 운 좋은 결과를 성능으로 읽었다.
**조치** `test_filter.py`가 **10시드 몬테카를로**를 돌리고 **최악값으로 판정**한다.
**재발 방지** 시나리오 판정 기준 자체가 최악값이다.

<a id="f-25"></a>
### F-25  시뮬레이터가 실기보다 조용했다

**증상** 시뮬 테스트는 다 통과하는데 실기 숫자가 안 맞는다.
**원인** `sim.py`의 잡음이 추측값이었고 **실기보다 3.4배 조용했다.**

| | 이전 추측 | 실측 (LSM6DS3) |
|---|---|---|
| 자이로 백색잡음 | 0.005 | **0.017** rad/s |
| 가속도 백색잡음 | 0.05 | **0.076** m/s² |
| 자이로 바이어스 | 0 | **[0.031, −0.065, −0.036]** rad/s (최대 3.7 °/s) |

**조치** 정지 로그에서 1차차분/√2로 실측해 이식. 테스트 한계값을 전부 올렸다.
**재발 방지** ❌ 관례뿐. **필터가 나빠진 게 아니라 시뮬이 정직해진 것이다.**
이 구분을 못 하면 다음 사람이 한계값을 도로 낮춘다.

<a id="f-26"></a>
### F-26  임계값을 datasheet에서 가져왔다

**증상** F-07의 직접적 원인.
**원인** 정지 판정 임계값을 센서 datasheet의 typical 값으로 잡았다.
실제 보드에 실제로 납땜된 센서는 그 값과 다르다.
**조치** 실제 20초 정지 로그에서 관측된 **최악값 바로 위**로 다시 잡았다.

```python
ZUPT_ACCEL_STD_MAX = 0.250   # 실측 최악 0.1475
```

**재발 방지** `config.py` 주석에 실측 출처와 "IMU를 바꾸면 재측정"을 명시.
**BMI088로 교체하면 이 두 줄은 반드시 다시 잡아야 한다.**

<a id="f-27"></a>
### F-27  `R_WHEEL_VELOCITY`가 튜닝된 적 없는 추측값이었다

**증상** 줄자 1.20 m 구간을 필터가 0.88~0.98 m로 냈다. 6개 구간 전부 **−22 %**,
방향이 아니라 배율이 틀렸다.
**원인** `R_WHEEL_VELOCITY = 0.05` m/s인데 로버의 주행 속도가 0.1 m/s다.
"측정값의 절반이 잡음"이라고 선언한 셈이라 필터가 자기 엔코더를 안 믿었다.
엔코더만 따로 적분하면 1.2303 m로 **줄자와 2.5 % 안에서 맞았다** — 센서가 아니라
필터가 버리고 있었다.
**조치** `R_WHEEL_VELOCITY = 0.012`. 로그에서 직접 잰 값이 근거다 —
바퀴 4개의 상호 불일치 0.0007 m/s, 평균속도 고주파 산포 0.0014 m/s,
엔코더 양자화 0.0015 m/s. **R은 센서 잡음이 아니라 모델 오차(슬립·반지름·스크럽,
줄자 기준 속도의 2.5~4 %)를 덮어야 하고**, 0.012는 둘 다 위에 있다.
**재발 방지** `analyze_drive.py`가 구간 길이를 줄자와 직접 대조한다.
NIS만으로는 못 잡았다 — 편향된 innovation도 R이 크면 "일관적"으로 보인다.

<a id="f-28"></a>
### F-28  정지 로그로 잡은 `R_GRAVITY`를 주행에 그대로 썼다

**증상** 주행 로그의 gravity NIS가 4.4 / 20 / 114 / 210 (목표 3). 거칠게 몰수록 컸다.
**원인** `R_GRAVITY = 0.0299`(3 cm/s²)는 **정지 상태**의 값이다. 주행 중에는 가속과
진동이 그보다 큰 비력을 만드는데 같은 신뢰도로 받아서 **진동을 기울기로 읽는다.**
게이트는 통과/차단만 정할 뿐 "얼마나 가까운가"를 반영하지 않았다.
**조치** `sigma = R_GRAVITY + R_GRAVITY_ACCEL_GAIN * | |a| - g |`.
`| |a| - g |`는 이 측정값 중 중력이 **아닌** 몫의 직접적인 척도다.
정지 중에는 0에 가까워 **기존 정지 튜닝이 그대로 보존된다.**
**재발 방지** 게이트가 아니라 모델 안에 들어 있어 호출자가 못 건너뛴다.

<a id="f-29"></a>
### F-29  `replay.py`가 모든 로그에서 헛경보를 냈다

**증상** 기록한 모든 로그에 "1 gaps over 3x average -- the loop stalled there".
**원인** 첫 구간 `t[0]`은 루프 주기가 아니라 **실행 시작부터 첫 행까지**의 시간이다
(포트 열기 + IMU 첫 샘플). 실제 루프는 p99 10.5 ms로 멀쩡했다.
**조치** 첫 구간 제외.
**재발 방지** **항상 켜져 있는 경고는 아무도 안 읽는다.** 그게 진짜 위험이다.

<a id="f-30"></a>
### F-30  heading이 없는 update가 global yaw를 고쳤다

**증상** `23:47` 직진 로그의 최종 yaw가 `+5.14°`. 단계 귀속은 wheel `+12.12°`,
NHC `−8.89°`, gravity `+5.39°`처럼 서로 큰 값을 상쇄했다. 좌우 encoder 차이로
예상되는 직진 회전은 약 `±0.1°`뿐이었다.

**원인** 측정식에 yaw가 없어도 `K=P HᵀS⁻¹`의 cross-covariance가 yaw correction을
만든다. 일반 ESKF의 재선형화가 global-yaw 비관측 방향을 정확히 보존하지 못했다.

**조치** 시작 연속 5초 정지 평균으로 gyro bias와 roll/pitch를 초기화한다.
wheel/NHC/ZUPT/gravity는 `R(q)ᵀ[0,0,1]` 방향의 Kalman gain을 투영 제거하고 update
전 yaw를 정확히 보존한다. 같은 로그의 최종 yaw는 `+0.07°`; 정렬시간 2–8초에서도
`0.25°` 이하였다.

**재발 방지** `test_filter.py`가 강한 임의 cross-covariance에서도 네 update의 yaw
변화가 `1e-9°` 미만인지 검사하고, 정렬 후 실제 gyro 회전은 남는지도 별도로 검사한다.

<a id="f-31"></a>
### F-31  무부하 사양을 실차 최고속도라고 불렀다

**증상** `31 rpm × 62.5 mm = 0.203 m/s`를 “실차 상한”이라고 문서화했다.

**원인** 공식 31 rpm은 24 V **무부하** 사양이다. 기본 Velocity Limit(44)=135의
`0.229 rpm/count` 환산값 0.2023 m/s도 command 범위일 뿐, 적재된 로버의 지속
최고속도를 측정한 값이 아니다.

**조치** 변수와 문서를 `MOTOR_SPEC_NO_LOAD_RPM`,
`COMMAND_WHEEL_SPEED_LIMIT_MPS`로 바꿨다. 시뮬레이터는 command 범위 안에서만
움직이지만, 실제 최고속도를 안다고 주장하지 않는다.

**재발 방지** `test_filter.py`가 모든 합성 시나리오의 바퀴 요구속도가 현재
Goal Velocity command 범위를 넘지 않는지 검사한다. 적재 지속속도는 별도 실험값이다.

<a id="f-32"></a>
### F-32  Arduino 센서축을 로버 body축으로 간주했다

**증상** `23:47` 마지막 직선 복귀가 갑자기 옆으로 벗어나고 최종 `y=15.9 cm`.
`23:34`도 중간 위치가 튀며 최종 `y=13.6 cm`였다. yaw는 각각 `0.07°`, `0.96°`라
heading만으로 설명되지 않았다.

**원인** 필터 계약은 `x=전진, y=좌측, z=위`인데 Arduino 보드 장착은 90°
돌아가 있었다. 세 로그 모두 wheel 종가속도와 sensor Y의 상관이 `-0.76~-0.82`,
회귀 기울기가 `-1.02~-1.11`인 반면 sensor X 상관은 `0.01~0.06`이었다.
전후 가속을 측면 가속으로 적분한 것이다.

**조치** `ARDUINO_IMU_TO_BODY=[[0,-1,0],[1,0,0],[0,0,1]]`을 accel/gyro 모두에
적용했다. 새 CSV는 `imu_frame=body`를 기록하고, 그 열이 없는 구형 Arduino 로그는
`logger.replay()`가 원본을 변경하지 않고 한 번 변환한다.

**재발 방지** `test_filter.py`가 행렬의 직교성, determinant `+1`, 축 변환을 검사한다.
BMI088 장착 시 별도 extrinsic을 다시 측정해야 한다.

<a id="f-33"></a>
### F-33  내부 strapdown 위치를 실제 차량 pose로 표시했다

**증상** 정지 직후 ZUPT 한 번에 최대 `4.0 cm`, 감속 중 wheel/NHC update가 각
`2 cm`씩 내부 위치를 옮겼다. `23:34`의 한 직선 구간에서는 gravity가 `+7.2 cm`,
다음 구간 wheel update가 `-11.2 cm`의 측면 위치 교차보정을 누적했다.

**원인** 어느 관측도 위치를 직접 재지 않지만 `K=P H^T S^-1`의 위치 행은
`P[p,v]`, `P[p,theta]` 때문에 0이 아니다. 이는 내부 posterior correction으로는
가능하지만, 실제 차체가 순간이동할 수 없는 연속 odometry frame으로 공개하면 안 된다.

**조치** 공개 pose를 `p_odom += R(q_ESKF)[v_wheel,0,0]dt`로 분리했다. 내부
`state['p']`는 필터 진단용으로 보존한다. replay GUI의 파란 선은 공개 pose,
자주색 점선은 내부 ESKF `p`다. R은 바꾸지 않았다.

**재발 방지** 테스트 중 내부 `state['p']`를 강제로 3.7 m 이동시켜도 공개 pose가
연속 wheel+attitude 모델을 유지하는지 검사한다.
