# 카메라 / Jetson 노트

> 로버 본체(오도메트리)와는 별개의 서브시스템이다. 이 문서는 Jetson Nano +
> USB 웹캠 작업에서 실제로 겪은 것들의 기록이다.
> 스크립트는 [`jetson/`](../jetson/), 촬영 결과물은 [`jetson/captures/`](../jetson/captures/).

Jetson Nano Developer Kit + USB 웹캠(Arducam B0201 / IMX291) 기반 로버.

## 하드웨어

| 항목 | 사양 |
|---|---|
| 보드 | Jetson Nano Developer Kit (JetPack 4.6.x / Ubuntu 18.04 / Python 3.6 / CUDA 10.2) |
| 카메라 | Arducam B0201 — IMX291 1/2.8", 1080p, 120° 광각, USB2.0 UVC |
| PC 연결 | micro-USB device mode — 젯슨 `192.168.55.1`, PC `192.168.55.100` |
| 시리얼 콘솔 | COM24 @ 115200 (네트워크가 죽었을 때의 최후 수단) |

## 접속

```bash
ssh <사용자명>@192.168.55.1
```

## 카메라 셋업

USB2.0 대역폭 때문에 무압축 YUYV로는 1080p가 5fps까지 떨어진다.
반드시 **MJPG fourcc를 해상도보다 먼저** 설정할 것 — 스크립트에 반영되어 있음.

```bash
sudo apt install -y v4l-utils
./jetson/cam_check.sh              # 장치 인식 + 지원 포맷 확인
python3 jetson/cam_test.py         # 한 장 찍어서 shot.jpg 저장 + 실측 fps
python3 jetson/cam_stream.py       # MJPEG 스트리밍 → PC 브라우저에서 확인
```

스트리밍 확인: PC 브라우저에서 <http://192.168.55.1:8080>

## 파일

- `jetson/cam_check.sh` — USB/v4l2 장치 및 지원 포맷 덤프
- `jetson/cam_test.py` — 단발 촬영 + 실측 fps 측정
- `jetson/cam_stream.py` — MJPEG HTTP 스트리밍 서버 (포트 8080)

## 주의

- 전원은 **배럴잭 5V 4A + J48 점퍼**. micro-USB 2A로는 카메라 + GPU 돌리면 리셋된다.
- 4GB RAM이라 스왑 4GB 필수.

## 검증된 설정값 (2026-09-05)

- 계정: `kit` / 호스트 `kit-desktop` / Ubuntu 18.04.6, L4T 커널 4.9.337-tegra
- 카메라: `0c45:6366` (Arducam B0201 / IMX291), `/dev/video0`
- OpenCV 4.1.1 사전 설치됨 — 별도 빌드 불필요

### `CAP_PROP_BUFFERSIZE`는 설정하지 말 것

1280x720 MJPG 기준 실측:

| 설정 | fps |
|---|---|
| `BUFFERSIZE=1` | 15.2 |
| `BUFFERSIZE=4` | 30.3 |
| 미설정(기본) | 30.3 |
| 미설정, 1920x1080 | 29.2 |

버퍼를 1로 잡으면 프레임을 하나 걸러 하나씩 놓쳐 정확히 절반이 된다.
지연 감소 목적이라면 버퍼 대신 별도 스레드에서 최신 프레임만 유지하는 방식을 쓸 것
(`cam_stream.py`의 `grabber()` 방식).

해상도·CPU 클럭(921MHz vs 1479MHz)·노출값(10~500)은 fps에 영향이 없었다.

### USB 가젯 네트워크 끊김

`l4tbr0` 브리지에 `rndis0`와 `usb0`가 동시에 물리면 주기적으로 통신이 끊긴다
(17초 주기, 4초간 100% 손실). `usb0`를 제거하면 손실률이 35% -> 12~22%로 떨어지지만
완전히 사라지지는 않는다. 안정적인 작업에는 유선 이더넷을 권장.

```bash
sudo brctl delif l4tbr0 usb0 && sudo ip link set usb0 down   # 재부팅 시 원복
```

## 카메라 테스트는 스트리밍으로 하지 말 것 (2026-09-05)

`http://192.168.55.1:8080` MJPEG 스트림은 USB 가젯 링크의 패킷 손실
(12~23%)에 그대로 노출된다. 연결이 한 번만 끊기면 스트림이 죽으므로
카메라 검증 수단으로 부적합하다. **젯슨 로컬에 녹화한 뒤 파일만
내려받는다.** 파일 전송은 재시도가 되므로 링크가 불안정해도 결국 성공한다.

```powershell
.\camtest.ps1              # 6초 녹화 -> sheet.jpg + full.jpg
.\camtest.ps1 -Secs 15 -H264
```

`cam_burst.py`는 프레임 간격 지터와 칸별 밝기까지 출력하므로,
끊김이 카메라 쪽인지 링크 쪽인지 로그만 보고 구분할 수 있다.
실측(6초, 1280x720 MJPG): **183프레임 / 30.4fps / 드롭 0회**.
카메라 자체는 안정적이다.

### 장치 번호를 하드코딩하지 말 것

USB 재열거가 일어나면 `/dev/video0`이 사라지고 `/dev/video1`만 남는다.
실제로 그렇게 됐다. `cam_burst.py`는 `/dev/video*`를 훑어 실제로 열리고
읽히는 것을 고른다.

카메라를 다른 프로세스(예: `cam_stream.py`)가 잡고 있으면 그냥
`can't open camera by index 0`이 뜬다. 먼저 `pkill -f cam_stream.py`.

### H264는 카메라가 지원하지 않는다

`v4l_formats.py`(v4l-utils 없이 ioctl로 열거)로 확인한 `/dev/video1`:

```
[MJPG] Motion-JPEG   1920x1080 / 1280x720 / 640x480 / 320x240  @30fps
[YUYV] YUYV 4:2:2     640x480 / 320x240                        @30fps
```

**H264 출력은 없다.** YUYV는 무압축이라 640x480이 한계이므로,
720p 이상에서는 MJPG가 유일한 선택지다.

다만 젯슨에는 하드웨어 인코더(`nvv4l2h264enc`, NVENC)가 있으므로
MJPG를 받아 H264로 재인코딩할 수는 있다. 파일이 훨씬 작아져
불안정한 링크로 내려받기 좋다 — 6초 4Mbps 기준 3.2MB.

```bash
./rec_h264.sh 6              # ~/camtest/clip.mkv
```

## 가로 띠가 흘러내리는 현상 (플리커 밴딩)

**원인은 카메라가 수동 노출 1ms에 묶여 있던 것.** `exp_probe.py`가 설정한
값이 그대로 남아 있었다. **UVC 컨트롤은 카메라 하드웨어에 저장되므로
프로세스가 끝나도, 스크립트를 지워도 풀리지 않는다.** 이게 이 문제의 핵심이다.

```bash
./cam_defaults.sh        # 컨트롤을 촬영 가능한 상태로 되돌린다
python3 v4l_ctrl.py /dev/video1     # 현재 값 확인 (v4l2-ctl -l 대용)
```

### 왜 띠가 "흐르는가"

한국 전원은 60Hz이므로 형광등·LED는 120Hz(주기 8.33ms)로 깜빡인다.
롤링셔터 센서는 행을 순차적으로 읽으므로, 노출 시간이 8.33ms의 배수가
아니면 행마다 받은 빛의 양이 달라져 가로 띠가 생긴다. 띠가 움직이는
속도는 조명 주파수와 프레임레이트의 맥놀이(beat)라서, fps가 30.4처럼
정수에서 조금만 벗어나도 천천히 흘러내린다.

노출값을 바꿔가며 실측한 결과(단위 100us):

| 노출 | 평균밝기 | 밴딩 % | 프레임당 이동 |
|---|---|---|---|
| 10 (1.0ms) | 10.9 | 32.7% | -0.1 px |
| 42 (4.2ms) | 35.6 | 9.9% | **-11.5 px** |
| 83 (8.3ms) | 55.1 | 5.7% | 0.0 px |
| 167 (16.7ms) | 81.6 | 4.5% | 0.0 px |
| 250 (25.0ms) | 98.6 | 4.0% | 0.0 px |
| 자동 | 88.0 | 4.3% | -0.1 px |

**8.33ms의 배수(83/167/250)에서는 띠가 완전히 정지한다.** 배수가 아닌
42에서는 프레임당 11.5px씩 흐른다. 어두울수록 상대 밴딩이 커진다.

수동 노출이 꼭 필요하면 **83, 167, 250 중에서 고를 것.** 그 외에는
`exposure_auto=3`(자동)이 맞다. `exposure_auto_priority=0`이라 자동이어도
fps는 30에서 안 떨어진다.

`power_line_frequency`(50Hz/60Hz)는 밴딩 진폭에 거의 영향이 없었다
(16.6% vs 16.3%). 이 드라이버에서는 노출값이 지배적이다. 그래도 60Hz(값 2)로
맞춰 둔다.
